## 1. 작품 구조 — 세 개의 자리

```
   ┌──────────────┐   별 전송 이벤트   ┌──────────────┐
   │  KIOSK       │ ───────────────▶ │  HUB         │
   │  태블릿 웹    │ ◀─────────────── │  Node 서버    │
   │  (관람객 1인) │   공동 우주 현황   │  + 공동 DB    │
   └──────────────┘                  └──────┬───────┘
          ▲                                 │
          │ 물리 버튼                        │ WebSocket 브로드캐스트
   ┌──────┴───────┐                  ┌──────┴───────┐   ┌──────────────┐
   │ Arduino Uno  │                  │ TouchDesigner │   │ 영수증 프린터 │
   │ (버튼 입력)   │                  │ 4면 프로젝션   │   │ (ESC/POS)    │
   └──────────────┘                  └──────────────┘   └──────────────┘
```

세 자리는 역할이 다르다. 섞지 않는다.

| | 무엇을 하는가 | 누구의 시간인가 | 문장이 보이는가 |
| --- | --- | --- | --- |
| **KIOSK** | 한 사람이 자기 시간을 기록하고 보낸다 | 나의 시간 | 보인다 (내가 지금 쓴 것만) |
| **WALL** | 모두의 빛이 감정별 별자리로 모인다 | 우리의 우주 | **보이지 않는다** |
| **RECEIPT** | 방금 보낸 그 한 사람에게만 쥐여 준다 | 나의 시간 | 보인다 |

> 벽에 문장이 가지 않는 것은 화면에서 감추는 방식이 아니라, **애초에 그 자리까지 문장이 건너가지 않는** 방식으로 한다. 기존 `SharedLight` 타입이 이미 그렇게 생겼다(`text` 필드가 없다). 그대로 계승한다.

## 2. 키오스크 화면 구조

전체화면 세로/가로 태블릿. 페이지를 옮기지 않고 **같은 하늘 위에서 장면만 겹쳐 바뀐다** — 기존 구조 그대로.

```
ATTRACT ──(손이 닿음 / 물리 버튼)──▶ INTRO ──▶ RECORD ──▶ EMOTION ──▶ CHOICE
                                                                        │
  ATTRACT ◀── THANKS ◀── RECEIPT ◀── SENT ◀── CONFIRM ◀─────────────────┘
     ▲                                  │
     └──────── 45초 무입력 자동 복귀 ──────┘
```

| 장면 | 이름 | 내용 | 나가는 길 |
| --- | --- | --- | --- |
| `attract` | 대기 | 공동 우주의 지금 모습이 조용히 흐른다. `{n}개의 빛이 모여 있습니다` | 터치 · 물리 버튼 |
| `intro` | 인트로 | 기존 인트로 문장 그대로, 박자도 그대로 | 자동 / 터치 |
| `record` | 기록 | 시간에 대한 정보 입력 (아래 3장) | 다음 |
| `emotion` | 감정 | 감정 선택 — 고르는 일이 곧 다음 걸음 | 선택 |
| `choice` | 간직 / 흘려보내기 | **감정과 완전히 분리된 별도의 선택** | 선택 |
| `confirm` | 확인 | 무엇을 보내는지 눈으로 보고 보낸다 | `시간을 보내기` |
| `sent` | 전송 | 별이 화면 밖(벽 쪽)으로 떠나간다. WS 전송 + 프린터 출력 | 자동 |
| `thanks` | 맺음 | `당신의 시간이 우리의 우주에 도착했습니다.` + 영수증 안내 | 자동 / `또 하나 보내기` |

운영용(관람객에게 보이지 않음)
- `admin` — 숨은 제스처(네 모서리 길게 누르기)로만 열린다. 연결 상태 · 오늘 전송 수 · 프린터 상태 · 재시도 큐.

### 기존과 달라지는 것 / 그대로인 것

| 그대로 둔다 | 달라진다 |
| --- | --- |
| 네 겹 레이어, 성운, 필름 입자, 배경별 비율 | 상단 내비게이션 **없음** (키오스크에 나가는 문을 두지 않는다) |
| 색 토큰 전부, 폰트, 여백 토큰 | ALL LIGHTS · NOW/THEN · 잔광 보기 · 다시 도착한 빛 **없음** (1인용 기능) |
| 인트로 박자, 도착 연출 | 걸음이 3 → 5로 늘어난다 (시간 정보 · 감정 · 간직/흘려보내기 분리) |
| `✦` / `○` 두 빛의 언어 | 별이 내 하늘에 남지 않고 **벽으로 떠난다** |
| `[data-safe]` 안전 영역 규칙 | 터치 대상 최소 **60px** (기존 44px은 태블릿 전시에 작다) |

## 3. 시간 기록 — 무엇을 묻는가

기존은 한 문장 하나뿐이었다. 전시에서는 '시간에 대한 정보'가 필요하므로 **한 걸음에 세 가지를 묻되, 둘은 선택이다.**

| 항목 | 필수 | 형태 | 비고 |
| --- | --- | --- | --- |
| 기억의 한 문장 | 필수 | 한 줄 입력, 80자 | 기존 `TEXT_LIMIT = 80`과 placeholder 그대로 |
| 그 시간은 언제인가 | 선택 | 연도 휠 또는 `올해 / 몇 년 전 / 아주 오래전 / 기억나지 않음` | 숫자 입력창을 두지 않는다 — 전시에서 키보드는 느리다 |
| 그 시간까지의 거리 | 자동 | `createdAt`(보낸 순간) − 고른 시점 | 별의 '빛이 건너온 거리'로 쓰인다 |

설계 원칙
- **날짜 피커를 쓰지 않는다.** 전시용 UI에 달력이 뜨는 순간 작품이 서식이 된다.
- 고른 시점은 **별이 얼마나 먼 곳에서 오는가**로만 쓰인다. 오래전일수록 더 멀리서, 더 느리게 도착한다.
- 아무것도 고르지 않아도 보낼 수 있다. 묻는 것과 시키는 것은 다르다.

## 4. 감정 — 별자리를 만드는 축

### 4.1 두 축은 직교한다

```
감정 (어떤 빛인가)                  →  색 · 모양 · 어느 별자리에 속하는가
간직 / 흘려보내기 (어떻게 둘 것인가) →  밝기 · 핵과 번짐의 비율 · 시간에 따른 변화
```

같은 '그리움'이라도 간직한 것과 흘려보낸 것이 있다. 둘은 **같은 별자리 안에서 밝기로 구분**된다.
`keep`/`letgo`의 수치는 기존 `tones.ts`를 **그대로** 쓴다(밝기 .78~1.0 / .42~.62, 핵 1.0 / 0.42, 갈래 유무, 잔광 0.12까지 25초).

### 4.2 색을 정하는 규칙 — 여기가 가장 조심할 곳

기존 작품의 색 원칙은 *"빛은 차갑지 않다. 푸른빛은 그림자에 극소량 섞이는 불순물이다"*이고,
배경별 팔레트에서 청보라는 **6%**뿐이다. 감정마다 선명한 색을 주면 이 규칙이 즉시 무너지고 작품은 SF 우주가 된다.

그래서 감정은 **무지개로 나누지 않는다.**

```
모든 감정의 색은 크림(#fff8e9) ~ 러스트(#b96b56) 사이의 좁은 띠 안에 둔다.
구분은 색상(hue)보다 ① 색온도의 미세한 차이 ② 별의 모양(form) ③ 하늘에서의 자리 로 한다.
가장 차가운 감정 하나에만 청보라(#3c3a68 계열)를 허용한다 — 전체의 한 자리.
```

감정 하나가 갖는 값(모두 데이터 테이블 한 곳에서 정의한다)

```
key        영문 식별자
name       화면에 보이는 우리말 이름   ← 확정 필요
glyph      기호
core       핵 색
halo       번짐 색
form       ember | cross | halo | soft  (기존 네 가지 생김새를 감정에 배정)
anchor     공동 우주에서 이 감정의 별자리가 자리잡는 중심 (ux, uy)
spread     그 중심에서 퍼지는 반경
```

### 4.3 감정 개수에 대한 권고

- **5~6개**를 권한다. 4개 이하면 별자리가 밋밋하고, 7개를 넘으면 좁은 색 띠 안에서 서로 구분되지 않는다.
- 네 면의 벽에 펼칠 때 면마다 1~2개 별자리가 놓이는 수이기도 하다.

> **감정의 정확한 이름은 아직 확정할 수 없다.** 기존 사이트에는 감정 항목 자체가 없고, 옛 버전의 다섯 감정 중 코드에서 복구되는 이름은 `놓아줌` 하나뿐이다(분석 문서 5장). 이름을 받기 전까지 코드에 임시 이름을 넣지 않는다 — 임시 이름은 반드시 어딘가에 남는다.

## 5. 공동 우주와 감정별 별자리

### 5.1 배치

기존 `placeInPersonalSky()`의 군집 알고리즘을 **감정 영역 안에서** 다시 쓴다.

```
1. 감정마다 하늘의 고정된 앵커 영역을 갖는다 (서로 겹치지 않게, 은하수 띠를 따라)
2. 새 별은 자기 감정의 영역 안에서 70% 확률로 이미 있는 빛 곁에 앉는다
3. MIN_SEPARATION .032 / CLUSTER_CAP 6 그대로 — 한 덩어리가 하늘을 차지하지 않는다
4. 영역이 꽉 차면 그 감정의 별자리가 바깥으로 조금씩 자란다 (전시 내내 자라는 우주)
```

### 5.2 선

```
같은 감정끼리만 잇는다.                   ← 이것이 '감정별 별자리'를 만드는 전부다
한 별이 잇는 선은 최대 2개 (DEFAULT_LINK_MAX)
LINK_RADIUS .34 · LINK_INK #f0e6d2 · 굵기 1.1px · 글로우 3.2px/.17  ← 전부 기존 값
새 별의 선은 1800ms에 걸쳐 배어 나온다
```

별이 수백 개로 늘어나면 선이 그물이 된다. 대비책을 미리 둔다.
- 감정별 별자리 안에서도 **최근 N개(예: 120개)만 선을 잇는다.** 오래된 별은 선을 놓고 빛으로만 남는다.
- 또는 별자리가 일정 크기를 넘으면 **둘로 나뉘어 새 별자리가 태어난다.** (전시가 길면 이쪽이 아름답다)

### 5.3 네 면의 벽

```
네 면을 하나의 연속된 하늘로 본다 (가로 4배 파노라마).
감정 앵커는 면 경계를 넘지 않도록 배치한다 — 별자리가 모서리에서 잘리면 안 된다.
면마다 1~2개의 감정 별자리 + 그 사이를 잇는 성운과 배경별.
새 별은 키오스크가 있는 쪽 면에서 들어와 자기 감정의 면으로 천천히 건너간다.
```

## 6. 데이터 구조

### 6.1 별 한 개 (서버에 저장되는 전체)

```ts
interface Star {
  id: string
  sessionId: string          // 익명. 같은 사람이 여러 개 보낸 것만 묶는 용도
  createdAt: number          // 보낸 순간 = 빛이 우리에게 도착한 순간

  text: string               // 80자. 키오스크와 영수증에만 쓰인다
  timeRef: {                 // '그 시간은 언제인가'
    kind: 'year' | 'yearsAgo' | 'longAgo' | 'unknown'
    value?: number
    label: string            // 화면·영수증에 그대로 찍히는 말
  }

  emotion: EmotionKey        // 감정 — 색 · 모양 · 어느 별자리
  keep: 'keep' | 'letgo'     // 간직 / 흘려보내기 — 밝기 · 시간에 따른 변화

  seed: number               // 같은 별은 언제나 같은 모습
  brightness: number         // keep/letgo의 범위에서 뽑는다
  form: 'ember' | 'cross' | 'halo' | 'soft'

  ux: number; uy: number     // 공동 우주에서의 자리 (서버가 정한다)
  constellation: EmotionKey  // = emotion. 명시해 두면 벽이 계산하지 않는다

  printed: boolean
  seq: number                // 전시 통산 번호. 영수증에 찍힌다
}
```

### 6.2 벽으로 건너가는 것 (`WallLight`)

```ts
// text · timeRef · sessionId 가 없다. 감추는 것이 아니라 오지 않는 것이다.
interface WallLight {
  id: string
  createdAt: number
  emotion: EmotionKey
  keep: 'keep' | 'letgo'
  seed: number
  brightness: number
  form: string
  ux: number; uy: number
  distance: number           // timeRef에서 나온 '빛이 건너온 거리' 0~1. 날아오는 속도에 쓴다
}
```

### 6.3 저장

- **SQLite 파일 하나**(`afterlight.db`) — 허브 PC 안. 외부 클라우드 없음, 네트워크가 끊겨도 전시는 계속된다.
- 전송 직후 **JSONL 추가 기록**도 함께 남긴다(`stars-YYYYMMDD.jsonl`). DB가 깨져도 하루치가 살아남는다.
- 키오스크는 보낸 직후 `localStorage`에 **마지막 전송 N건을 큐로** 들고 있다가, 서버 응답을 못 받으면 재전송한다. 관람객의 시간이 네트워크 때문에 사라지면 안 된다.

### 6.4 집계 (대기화면·벽·영수증이 함께 쓴다)

```
total            전체 빛의 수
byEmotion        감정별 수
byKeep           간직 / 흘려보냄 수
todayTotal       오늘 모인 수
```

## 7. 하드웨어 연동 구조

### 7.1 허브 (Node.js, 전시장 PC 한 대)

이 PC가 전시의 심장이다. 키오스크 태블릿·TouchDesigner·Arduino·프린터가 전부 여기에 붙는다.

```
HTTP        키오스크 정적 파일 서빙 (전체화면 웹앱)
WebSocket   :8080  — 키오스크 · TouchDesigner · 벽 미리보기가 모두 붙는 한 채널
Serial      Arduino Uno (USB, 115200)
USB/Network 영수증 프린터 (ESC/POS)
SQLite      공동 데이터
```

### 7.2 WebSocket 메시지 규약

모두 JSON 한 줄. TouchDesigner의 WebSocket DAT가 그대로 파싱한다.

```
키오스크 → 허브
  { "type": "star.send",  "star": { ...Star } }

허브 → 모두 (TouchDesigner가 기다리는 신호)
  { "type": "star.arrived", "light": { ...WallLight } }

허브 → 모두 (접속 직후 1회, 현재 우주 전체)
  { "type": "universe.snapshot", "lights": [ ...WallLight ], "stats": { ... } }

허브 → 키오스크 (대기화면 숫자 갱신)
  { "type": "stats", "total": 128, "byEmotion": { ... } }

Arduino → 허브 → 키오스크
  { "type": "button", "id": "send", "state": "down" }

허브 → 키오스크 (프린터 결과)
  { "type": "print.done", "starId": "...", "ok": true }

운영
  { "type": "heartbeat", "at": 1760000000000 }
  { "type": "admin.reset", "scope": "today" }
```

### 7.3 Arduino Uno

- Uno는 USB 시리얼(CDC)로만 붙는다. **태블릿이 iPad나 안드로이드면 Web Serial을 쓸 수 없다.**
  → 아두이노는 **항상 허브 PC에 꽂고**, 버튼 입력은 허브를 거쳐 WebSocket으로 키오스크에 간다.
  (키오스크를 Windows/Mac 터치 PC로 운영한다면 Chrome의 Web Serial로 직결도 가능하다. 그래도 허브 경유를 권한다 — 선이 하나 줄고 고장점이 하나 줄어든다.)
- 펌웨어는 **한 줄 JSON만 올려 보내는 가장 단순한 것**으로 둔다. 디바운스는 아두이노 쪽에서 처리한다.
  ```
  {"btn":"send","v":1}
  ```
- 버튼은 2~3개면 충분하다: **보내기 / 다음 / (관리자용 리셋)**. 화면 터치와 물리 버튼은 **항상 같은 일**을 해야 한다 — 둘 중 하나만 되는 순간이 있으면 관람객이 멈춘다.

### 7.4 TouchDesigner

- TD가 **WebSocket DAT 클라이언트**로 허브에 붙는다. 서버는 허브다(TD를 서버로 두지 않는다 — 키오스크가 TD의 생사에 묶이면 안 된다).
- 접속하면 `universe.snapshot`을 받아 전체를 그리고, 이후 `star.arrived`마다 별 하나를 추가한다.
- TD가 꺼져 있어도 키오스크는 정상 작동해야 한다. 벽이 멈춰도 사람은 계속 시간을 보낼 수 있다.
- 벽을 웹으로도 띄울 수 있게 **`/wall` 미리보기 페이지**를 같이 만든다. TD 연동 전에 벽 연출을 확인할 수 있고, 전시 중 TD가 죽었을 때의 비상용이기도 하다.

### 7.5 영수증 프린터

- 58mm 또는 80mm 감열 프린터, **ESC/POS**. 허브 PC에 USB로 연결하고 Node에서 직접 바이트를 쓴다.
  (브라우저 `window.print()`는 전시 무인 운영에 맞지 않는다 — 대화상자가 뜨고 여백 제어가 안 된다.)
- 출력은 **전송 직후 허브가** 한다. 키오스크가 프린터를 몰라도 되게 한다.
- 실패하면 큐에 쌓고 재시도. 종이가 없으면 관리자 화면에 뜬다. **프린터 실패가 별 전송을 막지 않는다.**

### 하늘 엔진

`starfieldEngine.ts`는 2557줄이고 이 작품의 심장이다. 선택지는 둘이다.

| | 방법 | 장점 | 비용 |
| --- | --- | --- | --- |
| **A (권장)** | 엔진을 그대로 가져와 공동 우주용으로 개조 (감정 영역 배치 · 같은 감정끼리 선 · 떠나가는 별) | 검증된 룩이 그대로 산다 | 개조 지점을 정확히 찾아야 한다 |
| B | 키오스크용으로 가볍게 다시 짠다 | 코드가 작다 | **같은 하늘이 나오지 않는다.** 권하지 않는다 |

벽(TouchDesigner)은 엔진을 쓰지 않는다. 대신 **엔진의 수치를 그대로 TD 파라미터로 옮긴다** — 색 팔레트 비율, 선 굵기와 투명도, 호흡 주기, 별 크기 범위. 수치표를 `docs/`에 따로 만들어 TD 담당자에게 넘긴다.

### 지켜야 하는 금지 사항 (기존 CLAUDE.md에서 그대로 가져온다)

- 관람객이 보낸 데이터를 **절대 삭제·초기화하지 않는다.** 흘려보낸 별도 마찬가지다.
- 흘려보내기는 삭제가 아니다. 희미해질 뿐 저장소에서 빠지지 않는다.
- 게임 UI · SF HUD · 네온 · 그라디언트 버튼 · 대시보드 미감 금지. 테두리와 상자를 두지 않는다.
- 개발용 버튼을 전시 빌드에 노출하지 않는다.
- 사용자 손짓 없이 `requestFullscreen()`을 부르지 않는다.

## 9. 단계별 개발 계획

각 단계가 끝날 때마다 **그 단계만으로 돌아가는 것**이 있어야 한다. 전부 만든 뒤에 켜 보지 않는다.

### 0단계 — 터 닦기 (0.5일)
- Vite + React 19 + TS 프로젝트 생성, `@/` 별칭
- 계승 파일 전부 복사, `npx tsc --noEmit` 통과
- **확인:** 빈 화면에 기존과 똑같은 하늘(성운 · 배경별 · 입자)이 뜬다

### 1단계 — 키오스크 혼자 돌아가는 전 과정 (2~3일)
- ATTRACT → INTRO → RECORD → EMOTION → CHOICE → CONFIRM → SENT → THANKS
- 서버 없이 메모리에만 저장. 감정 테이블은 **구조만** 만들고 이름은 비워 둔다
- 전체화면, 60px 터치 대상, 45초 무입력 복귀
- **확인:** 태블릿에서 처음부터 끝까지 손으로 한 바퀴 돈다

### 2단계 — 허브와 공동 데이터 (2일)
- Node + WebSocket + SQLite, `star.send` / `star.arrived` / `universe.snapshot` / `stats`
- 키오스크의 저장소를 `SkyRepository` 구현 교체로 갈아끼운다 (**UI는 한 줄도 건드리지 않는다**)
- 전송 실패 큐와 재전송
- **확인:** 태블릿 두 대에서 보낸 별이 한 숫자로 합쳐진다

### 3단계 — 벽 (3일)
- `/wall` 웹 미리보기: 공동 우주 배치, 감정별 별자리, 새 별 도착 연출
- 감정 앵커 배치와 선 규칙 확정, 별이 수백 개일 때의 밀도 실험
- **확인:** 보낸 별이 3초 안에 자기 감정 별자리에 합류한다

### 4단계 — TouchDesigner 연동 (2~3일)
- WebSocket DAT 클라이언트, 메시지 규약 연결
- 네 면 파노라마 매핑, 수치표 전달 및 룩 맞추기
- **확인:** 네 면에 투사한 상태에서 별 하나가 들어오는 것을 끝까지 본다

### 5단계 — Arduino (1일)
- 펌웨어(디바운스 + JSON 한 줄), 허브 시리얼 브리지
- 물리 버튼과 터치가 완전히 같은 일을 하는지 교차 확인
- **확인:** 화면을 만지지 않고 버튼만으로 한 바퀴 돈다

### 6단계 — 영수증 (1~2일)
- ESC/POS 출력, 레이아웃과 문구 확정, 재시도 큐
- 한글 폰트/인코딩 확인 (감열 프린터는 한글이 깨지기 쉽다 — **실물로 먼저 뽑아 본다**)
- **확인:** 전송 후 5초 안에 종이가 나온다. 종이를 빼도 전송은 계속된다

### 7단계 — 전시 운영 (2일)
- 무인 복구: 새로고침해도 상태가 돌아온다, WS 자동 재접속, 허브 재시작 시 DB에서 복원
- 관리자 화면, 전시 시작/종료 스크립트, 하루치 백업
- 부하 시험: 별 1,000개 상태에서 벽과 키오스크의 프레임 확인
- **확인:** 전원을 내렸다 올리면 아무도 손대지 않아도 전시가 다시 선다

### 8단계 — 리허설과 조율 (현장)
- 실제 밝기에서의 색 보정(프로젝터는 어둡고 노랗다 — 모니터에서 맞춘 색이 그대로 나오지 않는다)
- 관람객 동선, 글자 크기, 체류 시간 측정 후 박자 조정

누적 **2~3주** 규모(하드웨어 수급과 현장 조건에 따라 달라진다).

## 10. 확인이 필요한 것

진행 전에 답이 필요한 순서대로 적는다.

1. **감정의 정확한 이름과 개수** — 가장 급하다. 기존 사이트에 감정 항목이 없어 추출할 수 없었고, 옛 버전의 다섯 감정 중 코드에 남은 이름은 `놓아줌` 하나뿐이다. 이름을 받기 전까지 코드에 임시 이름을 넣지 않는다.
2. **키오스크 태블릿의 기종과 OS** — iPad / 안드로이드 / Windows 터치 PC. Arduino 연결 방식이 여기서 갈린다.
3. **허브로 쓸 PC가 있는가** — TouchDesigner를 돌리는 PC와 같아도 된다.
4. **영수증 프린터 모델** — 58mm인지 80mm인지, 한글 지원 방식.
5. **전시 기간과 예상 관람객 수** — 별자리가 포화되는 시점을 여기서 계산한다.
6. **키오스크가 몇 대인가** — 여러 대면 세션 충돌과 배치 경합을 2단계에서 함께 설계한다.

# 덧붙임 — 구현하면서 달라진 것 (2026-10-15)

## 1. 감정은 다섯이 아니라 **일곱**이다 (4장을 대체한다)

기획 당시에는 감정 이름을 구할 수 없어 다섯 개를 임시로 제안했다.
구현에 들어가면서 로컬 작업본에서 **확정된 일곱**을 찾았고, 임시 이름은 전부 버렸다.

```
행복 · 설렘 · 평온 · 불안 · 무기력 · 슬픔 · 기타
```

색을 다루는 규칙도 작업본의 것이 더 낫고, 더 정확하다.

| | 기획안(4.2장) | 실제 |
| --- | --- | --- |
| 감정의 색 | 핵과 번짐을 함께 바꾼다 | **핵은 건드리지 않는다. 번짐에만 0.34만큼 섞는다** |
| 색의 범위 | 크림~러스트의 좁은 띠 | 작업본이 이미 고른 일곱 색 (원색 없음) |
| 청보라 | 한 자리만 허용 | 불안·무기력·슬픔이 낮은 채도로 쓴다 |

핵과 회절 십자는 **언제나 간직/흘려보내기의 색**이다. 이 한 줄이
"감정마다 색을 다르게"와 "하늘이 알록달록해지면 안 된다"를 동시에 지킨다.
기획안이 제안했던 **모양(form) 구분은 그대로 살렸다** — 번짐에 0.34만 섞어서는
일곱이 서로 갈리지 않기 때문이다.

## 2. 별자리의 자리는 '반지름'이 아니라 '네 변'이다 (5.1장을 대체한다)

기획안은 감정마다 앵커 하나와 반지름(`spread`)을 주자고 했다. 실제로 해 보니
**조각들이 서로 겹쳤다.** 가로 거리가 `X_SQUEEZE`(0.62)로 눌려 셈해지는 탓에,
보기에는 떨어져 있어도 실제 영역은 물려 있었다. 검증 스크립트가 잡아냈다.

그래서 감정이 **네 변을 직접 들고 있게** 바꿨다. 하늘을 일곱으로 나눠 갖는다.

```
위 칸 (y 0.100~0.392)   행복 · 설렘 · 평온            셋 — 넓고 낮다
아래 칸 (y 0.472~0.880)  불안 · 무기력 · 슬픔 · 기타   넷 — 좁고 높다
```

위가 셋, 아래가 넷이라 너비가 다르므로 **높이로 그 차이를 메워 넓이를 고르게** 맞췄다.
한 조각만 먼저 차면 그 마음의 별자리만 뭉개져 보이기 때문이다.

## 3. 별자리는 자라지 않고 **촘촘해진다**

기획안은 "영역이 꽉 차면 바깥으로 자란다"고 했다. 그렇게 하면 옆 별자리와 섞여
'감정별'이라는 말이 무의미해진다. 대신 **최소 간격이 줄어든다**
(`lib/starMath.ts`의 `separationFor`). 사람이 모일수록 그 마음의 빛이 빽빽해진다.

- 한 별자리가 담는 빛: **대략 100개** (일곱을 합쳐 700개)
- 700개까지 넣어 보고 어느 두 별도 겹치지 않음을 확인했다 (`npm run check`)
- 그보다 더 쌓이면 **벽(네 면)으로 하늘을 넓힐 때**다. 네 면이면 하늘이 네 배가 된다

## 4. 하드웨어 규약을 새로 짓지 않는다 (7.2장을 대체한다)

기획안의 WebSocket 메시지 규약(`star.send` / `star.arrived` / …)은 **쓰지 않는다.**
작업본의 `bridge/`에 이미 서버와 신호 8종이 있고 52곳 시험까지 되어 있다.

```
star.sent · star.arrived · star.returning · star.returned
constellation.formed · constellation.named · scene.changed · sky.snapshot
```

그쪽이 이미 해결해 둔 것들 — 문장이 벽으로 새지 않게 두 겹으로 막기,
점검 신호와 관람객의 빛을 `origin`으로 가르기, 끊겨도 하늘이 멈추지 않기,
밀린 신호를 쏟지 않되 `sky.snapshot` 한 장만 들고 있기 — 를 다시 설계할 이유가 없다.

→ 4단계(TouchDesigner)는 **새 규약을 만드는 일이 아니라, 이 키오스크를
그 다리에 붙이는 일**이 된다.
